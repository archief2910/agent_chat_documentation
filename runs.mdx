`POST /api/v1/chat/completions` and `POST /api/v1/chats/{chatId}/messages` return before the model finishes. This route is how you read that work.

<ParamField path="runId" type="string" required>
  The `runId` from the `202` response.
</ParamField>

<RequestExample>

```bash
curl https://agent-chat-backend-production.up.railway.app/api/v1/runs/run_123 \
  -H "Authorization: Bearer $TOKEN"
```

</RequestExample>

<ResponseExample>

<ResponseField name="status" type="string" required>
  `queued`, `thinking`, `working`, `waiting`, `stopping`, then one of `completed`, `failed`, or `cancelled`.
</ResponseField>

<ResponseField name="progress" type="integer" required>
  Step count as a percent from 0 to 100. It reaches 100 only when the status is terminal.
</ResponseField>

<ResponseField name="routedModel" type="string">
  The model OpenRouter Free selected. The request itself is always `openrouter/free`.
</ResponseField>

<ResponseField name="assistantMessage.content" type="array">
  Saved blocks in order: text, tool use, tool result, and assets. A reload reads these from Postgres. The live token stream can be ahead of the last checkpoint.
</ResponseField>

<ResponseField name="waitpoint" type="object">
  Present while the run is paused for a plan or credit approval. `kind` is `options`, `plan`, `credit`, or `media`. Answer it with `POST /api/v1/waitpoints/{id}/respond`. The same answer again is accepted. A different answer is `409`.
</ResponseField>

## Other run calls

| Call | Result |
| --- | --- |
| `POST /api/v1/runs/{runId}/cancel` | Status becomes `stopping`, then `cancelled`. |
| `POST /api/v1/runs/{runId}/retry` | Allowed only when the run is `failed` or `cancelled`. Sends the same user text and attachments as a new turn. Optional `clientMessageId` makes that retry idempotent. |
| `POST /api/v1/runs/{runId}/realtime-token` | A new read token for stream `agent-output`. Keep polling this status route if the stream disconnects. |

`queued` means the turn is saved and the worker has not started. `thinking` and `working` mean the worker is running. `waiting` means a waitpoint is open.
